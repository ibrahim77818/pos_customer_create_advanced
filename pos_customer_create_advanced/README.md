# POS Customer Search & Quick Create Advanced (`pos_customer_create_advanced`)

Odoo 18 (Community & Enterprise). Depends on `point_of_sale` and `phone_validation` (both Community;
`phone_validation` is auto-installed with Discuss).

## Features

1. **Substring phone search, formatting-insensitive**
   * Local search (loaded customers): phone and mobile are also indexed as digits only, and a
     phone-like query (`+966 50`, `(555) 014`, `014-45`, `٠٥٥ ١١١`) is reduced to ASCII digits,
     so any digit sequence matches anywhere in the number: `0144567` finds `+1 (555) 014-4567`.
   * Leading zeros of the query are ignored, so the local way of typing a number (`0500477818`)
     finds it when it is saved with its country code (`+966500477818`).
   * Server search ("Search more" and the automatic lookup): a phone-like query searches only
     `res.partner.pos_phone_digits`, a stored field holding the digits of phone and mobile, with a
     trigram (GIN) index. Text queries keep the standard fields (name, company, phone, mobile,
     email, VAT), matched anywhere in the value.
   * Automatic server lookup: a phone query (3+ digits) with no local match is sent to the server
     once the search settles (Odoo 18's search box debounces 500 ms), once per query.
     Offline/timeouts are silent.
2. **Phone pre-filled on creation**: a phone search with no result shows
   "Create customer with phone ...". That button and the standard **Create** button both open the
   contact form (Odoo 18 creates customers in `base.view_partner_form`) with `phone` = the searched
   number. Odoo 18's own phone onchange then displays it in international format.
3. **Default customer name per POS**: *Point of Sale > Configuration > Settings > Customer
   Onboarding*. When enabled, a new customer saved from that POS with a phone/mobile and no name
   gets the configured name. A typed name always wins; existing customers, child contacts and
   addresses are never renamed; with the option off the contact form keeps its required name. The
   form shows "If left empty, saved as <name>" under the name field.
4. **International phone format (E.164) per POS**, on by default (*Customer Onboarding >
   International Phone Format*). When a cashier saves a customer, `phone` and `mobile` are stored as
   `+<country code><number>`, as SMS and WhatsApp gateways expect:
   * `0500477818`, `050 047 7818`, `00966500477818`, `٠٥٠٠٤٧٧٨١٨` → `+966500477818` (Saudi Arabia);
     works for every country through Odoo's `phone_validation` (Google libphonenumber metadata).
   * Country used: the one selected in the contact form, else the customer's existing country, else
     the POS company's country. Odoo 18's contact form formats a number as soon as it is typed, so
     the cashier should choose a foreign country before typing the number.
   * A number that is not valid for that country is saved as typed: the cashier is never blocked.
   * Editing a customer from the POS only reformats the numbers the cashier changed.
   * Applies only to the contact form opened from the POS (context key `pos_cca_config_id`); the
     same form opened from Contacts, imports and API calls are not changed. With the option off,
     Odoo 18 still applies its own phone onchange (spaced international format).
   * Needs the `phonenumbers` Python library (`pip install phonenumbers`); the settings page shows
     a warning when it is missing, and numbers are then saved as typed.

## Performance (measured, 1,000,000 partners, PostgreSQL 16)

Server query per lookup, `LIMIT 30`, ordered like Odoo (`complete_name, id DESC`). The standard
column runs the exact SQL generated by Odoo 18's POS customer search.

| Query | Matches | Odoo 18 standard | This module |
|---|---|---|---|
| `0551112233` (new customer) | 0 | 4.2 s | **1.5 ms** |
| `757 4187` | 34 | 3.7 s | **1.2 ms** |
| `4187` | 916 | 0.37 s | **3.1 ms** |
| `456` | 8,732 | 0.30 s | **6.4 ms** |

Install on 1M partners: column backfill in SQL ~22 s, index build ~3 s (index ~36 MB).
Without `pg_trgm` the same query is a scan of one short column: ~0.24 s.

### Deployment notes

* Odoo 18 loads the **100 most frequent customers** into the POS by default (system parameter
  `point_of_sale.limited_customer_count`); every other customer is found through the server. The
  automatic server lookup does this as the cashier types.
* `pg_trgm` is a trusted extension (PostgreSQL 13+): the module enables it when the Odoo database
  user owns the database. Otherwise run `CREATE EXTENSION pg_trgm;` as a superuser, then upgrade
  the module; a warning is logged until then.
* Cashiers need **Extra Rights > Contact Creation** to create customers (standard Odoo 18; every new
  user gets it from the default user template).
* Trade-off: on the server, a query made of digits only (e.g. `2023`) searches phone numbers, not
  names. Loaded customers are still matched on name locally.
* Upgrading from the 16.0 version: the 16.0 index (`res_partner_pos_phone_digits_index`) is dropped
  and rebuilt under the Odoo 17/18 name (`res_partner__pos_phone_digits_index`).

## Technical notes

* POS JS: ES modules in `static/src/app/`, extending `PartnerList` (the customer dialog),
  `ResPartner.searchString` and `PosStore.editPartner/editPartnerContext` with `patch()`. Nothing is
  written on reactive records during render; per-customer digits are cached in a `WeakMap`.
* `PartnerList.getNewPartners` is replaced (core builds its domain inline); the call is the same
  `pos.data.searchRead` and the domain is exposed through `_ccaGetPartnerSearchDomain(query)`.
* Odoo 18 removed `res.partner.create_from_ui`: customers are saved by the contact form. The POS
  passes `pos_cca_config_id`, `pos_cca_phone` and `pos_cca_default_name` in the form context; the
  server applies them in `default_get`, `create` and `write`. The form view extension relaxes the
  required name only when `pos_cca_default_name` is in the context.
* The hint field is also provided by `default_get`: Odoo 18's first onchange of a new record fills
  every field without a value from `default_get`, before computed fields run.
* The POS searches `pos_phone_digits` with `like`, not `ilike` (18.0.1.2.1). Odoo 18 wraps every
  `ilike` in `unaccent()` when the database has the `unaccent` extension, and removed the field
  option that turned this off; the trigram index on the plain column is then not used (~0.37 s
  instead of ~2 ms on 1M partners). Digits have no case, so `like` gives the same results.
* Digit normalisation exists in three places that must agree: `phone_digits()` and
  `PHONE_DIGITS_SQL` (`models/res_partner.py`) and `digitsOnly()` (`static/src/app/phone_utils.js`).
